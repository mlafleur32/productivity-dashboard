## What this project is

A **native macOS application** (SwiftUI, Swift, built in Xcode) that acts as a
personal AI assistant. It presents a **read-only dashboard** surfacing:

- **Important email** — messages that likely need attention or a reply.
- **Unsubscribe candidates** — newsletters / marketing the user likely wants out of.
- **Scams & phishing** — suspicious messages flagged for the user.
- **Upcoming calendar events** — from the user's calendars.
- **Tasks** — action items **extracted from email by AI analysis** (not a manual
  task list, not Apple Reminders — see Decisions).

Later iterations may add **email organization** and **calendar organization**
actions, but ONLY after the read-only dashboard is solid and ONLY with explicit
per-action user confirmation (see Roadmap).

## Architecture

Top to bottom:

1. **Dashboard UI (SwiftUI)** — sections for Important Email, Unsubscribe,
   Scams & Phishing, Calendar, Tasks, plus (later) the Assistant, Recently
   Archived and Recently Created sections.

2. **Analysis layer — split in two:**
   - **Local rules engine** (runs on-device, on ALL mail, free): sender
     reputation, known-newsletter patterns, `List-Unsubscribe` header detection,
     obvious-scam heuristics.
   - **Cloud client (Claude API)**: importance scoring, scam/phishing judgment,
     and task extraction. Called **only** for mail that is (a) on the
     cloud-allowlist AND (b) genuinely ambiguous after local rules.

3. **Data access:**
   - **Calendar:** EventKit.
   - **Email:** **IMAP** connection. User enters server + credentials. Use an
     **app-specific password** (generated by the email provider), never the main
     account password.

4. **Storage:**
   - **macOS Keychain** for ALL credentials, tokens, and the API key. Never in
     code, config files, plaintext, or anything synced. **iCloud Keychain sync
     must be off for this app's items** — keep entries local-only to this Mac.
   - **SwiftData** for the small local database (allowlist + classification
     cache). Chosen over Core Data because the model is tiny, the app is
     SwiftUI-throughout, and there is no legacy to preserve. Define models with
     `@Model` Swift classes — no .xcdatamodeld file needed.
   - **No CloudKit. No iCloud sync of the SwiftData store.** This is a
     single-device, local-only app by design. The classification cache encodes a
     behavioral profile of the user's inbox (who they correspond with, who they
     marked as scams, who's on the allowlist) and that profile must not leave the
     Mac. When Xcode / Claude Code offers to enable CloudKit or iCloud capability
     for the SwiftData container: decline. If multi-device support is ever
     wanted, revisit deliberately — don't enable sync as a default.
   - **Persisted entities are minimal by design** (privacy-driven):
     - **Allowlist:** sender identifier + cloud-eligible status + timestamp.
     - **Classification cache:** message ID + category (important / newsletter /
       scam / other) + timestamp. **Do NOT persist raw email bodies, subjects,
       or sender names beyond what is strictly needed to recognize the message
       again.** Cache results, not content.
   - **Explicit `modelContext.save()` after every allowlist mutation.**
     SwiftData's auto-save can fail silently in some situations; a missed save on
     the allowlist would fail privacy-safe (sender reverts to local-only) but is
     still a UX bug. Don't rely on auto-save for the allowlist specifically.
   - Analysis results cached so each email is **analyzed at most once** (on first
     arrival). Frequent polling is cheap; re-analysis is what costs money — avoid it.

## Testing

- **Use Swift Testing as the default** for all unit tests and business logic
  (`@Test`, `#expect`, `#require`, parameterized tests). This is a new project on
  Xcode 26 with no legacy XCTest code, so there's no reason to start on XCTest.
  Swift Testing is built into Xcode 16+ with no dependency to add — just create
  files in the test target.
- **Use XCTest only** for UI tests (XCUITest) or performance tests, which Swift
  Testing does not cover. The two frameworks coexist in the same target, so this
  is not an either/or lock-in. UI tests are not needed early; the first iteration
  is a read-only dashboard.
- **Highest-priority tests come first, and they are security tests, not UI tests.**
  The three places a silent bug would breach the privacy/safety boundary:
  1. **The allowlist gate** — prove that an unrecognized / non-allowlisted sender
     NEVER reaches the network and is handled local-only. This is the single most
     important test in the project. Fail-safe behavior must be verified, not assumed.
  2. **Email-stripping logic** — prove quoted reply threads and signatures are
     removed before any content is eligible for an API call.
  3. **The action confirmation gate (Stage 6+)** — prove that no mailbox write
     command can ever be issued without a user-confirmed action: cancel mints
     nothing, and the write layer is unreachable except through the confirmed
     type. Treat as a release gate, peer to the allowlist gate.
- Use **parameterized tests** for the rules engine (newsletter detection,
  `List-Unsubscribe` parsing, scam heuristics): one test fed a table of
  (input, expected-category) cases, since these rules will be tuned repeatedly as
  misclassifications surface.

## Security & Privacy — NON-NEGOTIABLE

These come directly from the user's stated diligence requirements. Do not relax
them without explicit instruction in conversation.

1. **The allowlist gate is the spine of the design.** Every email passes through
   ONE gate before any analysis. The gate asks: *is this sender on the
   cloud-allowlist?*
   - **Yes** → eligible for Claude API analysis (after stripping quoted threads
     and signatures).
   - **No (default for anything unrecognized)** → NEVER leaves the Mac; handled by
     local rules only.
   - Implement as an **ALLOWLIST, not a blocklist.** Anything unrecognized must
     **fail safe** (stay local). The user promotes senders to "OK for cloud"
     deliberately. This means privileged senders (lawyer, accountant, medical,
     etc.) and any sender not yet seen are local-only by default.
   - This gate must sit **in front of** the analysis layer so there is **no code
     path** where a non-allowlisted email reaches the network. Build it before the
     thing it guards.

2. **Consequence the user has accepted:** because tasks are extracted by AI
   analysis, tasks are only produced from **allowlisted** senders. Non-allowlisted
   mail produces no tasks. This is expected behavior, not a bug.

3. **Minimize what is transmitted.** Strip quoted reply threads and signatures
   before any API call. Send the least content needed for the judgment.

4. **No telemetry / no extra network calls.** The app makes only the network calls
   its features strictly require (IMAP fetch; Claude API for allowlisted mail). No
   analytics, no phone-home.

5. **No plaintext persistence of private content** unless the user explicitly
   opts in. Process email/calendar content in memory; cache analysis *results*,
   not raw private bodies, where avoidable.

6. **Every destructive or outbound action requires explicit user confirmation**
   (archive, delete, unsubscribe, send, create/decline event). Nothing that
   modifies or sends fires automatically. (Relevant in later iterations — the
   first iteration is strictly read-only.)

### Why the Claude API is acceptable here
The owner verified (and should re-verify against current Anthropic docs, since
policies change) that:
- The **Anthropic API is a commercial product**; by default Anthropic does **not
  train** on inputs/outputs from commercial products. The Sept 2025 consumer
  train-by-default change explicitly **excluded commercial customers**.
- Training only happens if the user explicitly opts in (e.g. feedback buttons,
  tester programs) — so the app should make plain API calls and submit no feedback.
- API logs are retained briefly (reduced to ~7 days as of Sept 2025) then deleted;
  safety-flagged content may be retained longer. Zero Data Retention exists but is
  typically an enterprise arrangement.

Re-confirm at https://docs.claude.com and https://privacy.claude.com.

## Key decisions (settled with the user)

- **Email source (iteration 1):** IMAP, user-entered credentials, app-specific
  password, stored in Keychain.
- **Tasks:** extracted from email by AI analysis (allowlisted senders only).
- **Pace:** guided, explain Xcode mechanics, build in stages.
- **AI location:** cloud (Claude API) for allowlisted mail; local rules for
  everything else. Tokens are NOT the constraint — the privacy boundary is. Per-email
  cost is a fraction of a cent if results are cached and never re-sent; analyze each
  email once on arrival.
- **First build is READ-ONLY.** No actions that modify or send anything.
- **Actions start with archive only (Stage 6, settled 2026-07).** The smallest,
  reversible write proves the machinery (IMAP write path, confirmation gate,
  action log + undo, release-gate tests) before riskier actions are considered.
  Confirmation UX: an Archive button on every message row; a dialog names the
  exact message (sender + subject) with Confirm/Cancel. Verdict sections suggest
  by proximity only — no verdict or extracted task ever preselects or
  parameterizes an action (THREAT_PATTERNS.md injection firewall).
- **Action log is privacy-minimal (settled 2026-07):** message ID, sender
  address, action kind, timestamp, undo handle — NO subjects or bodies, same
  discipline as the classification cache. Explicit save after every mutation.
- **Unsubscribe posture (banked for a later stage, do not relitigate):** HTTP
  one-click (RFC 8058) is acceptable, each behind explicit confirmation, NEVER
  offered on scam-classified mail. mailto-only senders get handed to Apple Mail
  as a pre-filled draft — the app itself never sends mail (SMTP stays banned).
- **Cloud "suspicious" verdicts stay hidden (settled 2026-07-05):** deliberately
  excluded from the Scams section (cry-wolf risk). Do not resurface unprompted.
- (Dropped earlier: a patient-portal login feature was considered and
  **removed** due to legal/ToS/feasibility risk. Do not reintroduce.)

## Roadmap (build in this order)

**Stage 1 — Project skeleton + dashboard shell.** ✅ Done. Empty macOS
SwiftUI app that builds, runs, and shows the dashboard layout with placeholder
data.

**Stage 2 — Calendar (EventKit).** Read and display real upcoming events. First
encounter with Apple's permission prompt. Add the calendar usage description to
Info.plist / target settings. The Swift Testing unit-test target already exists
from project setup; first tests land here as soon as there's logic worth testing.

**Stage 3 — IMAP email fetch.** Connect, pull recent messages, display them raw
(no analysis yet). This is where Keychain + app-specific-password setup happens.
Ask the user their email provider to give exact app-password steps + IMAP server
settings. **Write Swift Testing tests for the email-stripping logic** (quoted
threads + signatures removed) as soon as that logic exists.

**Stage 4 — Local rules engine + allowlist gate.** Categorize everything
on-device. The privacy gate must be fully in place here. Allowlist management UI
(user promotes senders to cloud-eligible). **Write the allowlist-gate fail-safe
test here and treat it as a release gate** — unrecognized sender must never reach
the network. Parameterize the rules-engine tests.

**Stage 5 — Claude API analysis.** ✅ Complete + polish pass (2026-07-05).
Importance, scam/phishing detection, task extraction — for allowlisted,
ambiguous mail only. API key in Keychain. (Stages 1–4 also complete.)

**Stage 6 — Archive action + confirmation gate.** ✅ Complete, live-validated
2026-07-09. The first write feature. A second compile-time gate mirrors
CloudEligibleMessage: `ConfirmedArchiveAction` is mintable ONLY by the
confirmation flow's confirm() (cancel mints nothing), and the IMAP write
layer accepts nothing else — see Actions/ArchiveConfirmation.swift and the
ArchiveConfirmationGateTests release-gate suite. As built:
  - Fetch paths open INBOX with EXAMINE (read-only by construction); the
    archive/unarchive executors hold the app's only SELECTs.
  - Archive destination discovered via RFC 6154 SPECIAL-USE attribute
    (`\All` preferred, else `\Archive`; refuses rather than guesses a
    localized name). Archive = UID MOVE out of INBOX; undo handle = new UID
    from UIDPLUS COPYUID (Gmail reports it — verified live).
  - Action log: ArchiveLogEntry (privacy-minimal, no subjects/bodies) +
    Recently Archived dashboard section with one-click undo. Undo needs no
    dialog (restores prior state, same reasoning as one-click demote) and
    refuses to mark an entry undone when the reverse move produced no
    COPYUID (stale handle — never falsely "undone").
No new Apple permissions were needed.

**Stage 7 — Unsubscribe action + confirmation gate.** ✅ Complete,
live-validated 2026-09-16 on Gmail with three real senders: one-click 202 →
Unsubscribed; mailto → correct Apple Mail draft; one-click 307 → same-site hop →
405 → "Open in Gmail" → marked "Unsubscribed in Gmail". Row
status replaces the button after any recorded choice (no accidental
repeats; right-click to redo). The second write feature, built on Stage 6's
machinery and the settled unsubscribe posture (Key decisions). A third
compile-time gate, same idiom as ConfirmedArchiveAction.
  - **Method selection comes ONLY from headers** — never from a cloud verdict
    or extracted task (injection firewall). Priority:
    1. **RFC 8058 one-click:** `List-Unsubscribe` has an `https:` URI AND
       `List-Unsubscribe-Post: List-Unsubscribe=One-Click` AND the trusted
       Authentication-Results says `dkim=pass`. No dkim=pass → no one-click
       (settled 2026-09-15).
    2. **mailto:** handed to Apple Mail as a pre-filled draft (only to,
       subject, body kept — cc/bcc/other params dropped). The app never sends.
    3. **Plain https link only (no One-Click Post header):** NOT offered
       (settled 2026-09-15). Row says there's no safe unsubscribe option and
       suggests Archive.
  - **Eligibility (`UnsubscribeOffer`, fileprivate init):** local category is
    `.newsletter`; NOT local `.scam`; no cloud `phishing` OR `suspicious`
    verdict; no trusted `dmarc=fail`; a usable method from the list above.
    The confirmation flow's request() accepts only an offer; confirm() is the
    single mint site for `ConfirmedUnsubscribeAction`; cancel mints nothing.
    The executors accept only the confirmed type.
  - **One-click request hardening:** HTTPS only, default port only, POST with
    body `List-Unsubscribe=One-Click` and nothing else; ephemeral URLSession
    (no cookies, no cache, no credential storage); URLSession never follows
    redirects — the executor handles AT MOST ONE 307/308 hop to a URL that
    passes every safety rule (settled 2026-09-16 after a live 307): same
    site (approved host or subdomain) is followed automatically; a
    different site STOPS and shows a second confirmation naming the new
    host ("Send your unsubscribe to another company?" — gated by
    PendingUnsubscribeRedirect / ConfirmedUnsubscribeRedirect, cancel sends
    nothing). 301/302/303, unsafe targets and a second hop are refused;
    the alert names the attempted host; no
    userinfo in URL; IP-literal, `localhost`, `.local` and single-label hosts
    rejected; short timeout. Success = any 2xx.
  - **Confirmation dialog** names sender + subject AND the destination (the
    one-click host, or the mailto address), and states the action can't be
    undone from the app.
  - **Action log is privacy-minimal:** message ID, sender address, method
    (oneClick / mailto), timestamp, outcome. **No URLs or mailto addresses
    persisted** — unsubscribe links embed per-recipient tokens. No undo.
    Explicit save after every mutation. Senders already unsubscribed show
    "Unsubscribed" instead of the button.
  - **When the app can't unsubscribe safely (settled 2026-09-16, after a
    live 307→405 from a real sender):** the failure alert offers "Open in
    Gmail" (Gmail accounts only) and, if the header lists a safe mailto,
    "Unsubscribe by Email…" (back through the normal confirmation). Gray
    "no safe option" rows also get "Open in Gmail". The Gmail link is built
    ONLY from the message's own Message-ID + the user's account, fixed host
    https://mail.google.com, opener re-checks the host; it is not a
    sender-chosen page, so no confirmation — the user unsubscribes in Gmail.
  - **New data access:** `List-Unsubscribe-Post` added to the IMAP header
    FETCH. **No new entitlements** (network.client already covers HTTPS;
    NSWorkspace mailto handoff needs none).
  - **Release-gate tests:** scam / phishing / suspicious / dmarc=fail mail can
    never produce an offer; cancel mints nothing; double-confirm mints once;
    parameterized ListUnsubscribeParser + URL-safety tables; one-click
    executor tested against a fake transport (never a real socket).
  - Steps: Design → A (header fetch + parser) → B (eligibility + gate) →
    C (executors) → D (UI + log) → E (live validation).

**Stage 8 — Create calendar event + confirmation gate.** ✅ Complete,
live-validated 2026-09-28 on a real calendar: typed and email-suggested
events, a time read from the body of a thread, the optional notes reference,
the created banner with Undo, the row hint and the "Event created" marks.
Designed 2026-09-16, built in steps A–D6 (see below). The first calendar
WRITE. Same machinery as Archive (Stage 6): typed gate, per-action dialog,
privacy-minimal log, undo.
  - **Scope decisions (Matt, 2026-09-16):**
    1. Create events first. Accept/decline is NOT possible through EventKit
       (participant status is read-only to apps); any invite-response feature
       must be a hand-off to Google/Apple Calendar — a later stage.
    2. **Blank form, or suggested from an email on request (revised by Matt
       2026-09-16, same day).** Besides New Event, a message row offers
       "Make Event from Email…", which opens the SAME form prefilled with
       suggestions. Nothing is saved until Matt reviews every field and
       confirms. This deliberately revises the injection-firewall rule —
       see "Suggested events" below and THREAT_PATTERNS.md.
    3. **Calendar picked in the form**, listing only calendars that accept
       new events (`allowsContentModifications`; no subscribed, birthday or
       read-only calendars), defaulting to the macOS default calendar —
       never chosen by an email.
  - **Suggested events (settled 2026-09-16):**
    - **On-device only.** Suggestions come from Apple's `NSDataDetector`
      (date/time detection) run on this Mac over the subject and the
      stripped plain-text body. The body fetch is the existing local IMAP
      fetch; nothing is sent to the Claude API for this, so it works for
      every sender, allowlisted or not.
    - **Which detection wins (revised by Matt 2026-09-18):** the LAST time
      in the body beats the subject — in a thread the quoted history is
      stripped first, so that is the newest message's latest word on it.
      The subject is the fallback when the body has no date.
    - **What may be suggested:** title (the subject, trimmed/sanitized,
      ≤200), start, end (detected duration, else 1 hour), all-day (date
      without time). Nothing else — no links, notes, location, invitees,
      and never the calendar.
    - **When it's offered:** on the row's context menu, and — Step D5,
      Matt 2026-09-27 — as a hint line on the row itself when a background
      on-device scan found a date ("Thu, Oct 1 at 12:30 PM — make event…").
      Never on local scam, cloud phishing/suspicious or trusted dmarc=fail
      mail. The hint only opens the same reviewed form; it creates nothing.
    - **The hint scan (D5):** runs after each load, over personal/important
      mail only (never newsletters or scam), newest ≤12 unscanned messages,
      once per message per session. It fetches the body over the existing
      LOCAL IMAP connection, reads it and drops it; bodies fetched in a pass
      are shared with the cloud pass so a message is fetched once. Only the
      detected start and all-day flag are kept, in memory, for the session —
      no body text, nothing persisted, nothing sent anywhere. The cloud
      allowlist gates the CLOUD path only; a local read is not a cloud send,
      and a release-gate test holds that line.
    - **Review is mandatory:** the form and the confirmation dialog both
      say "Suggested from an email from <sender> — check every field". A
      suggestion with no detected date opens with the date empty/required.
    - **Gate unchanged:** a suggestion is just initial form values; the
      same validator mints `NewEventDraft` and the same dialog mints
      `ConfirmedCreateEvent`. The log records source kind (manual /
      fromEmail) — no sender, subject or body. **Revised D3 (Matt
      2026-09-17):** for fromEmail events the log also stores the email's
      message ID (`sourceMessageID`), used only to show "Event created" on
      that email's row; manual events store none.
  - **What an event can contain:** title (required, trimmed, ≤200 chars, no
    control characters), start, end (end after start), all-day flag, target
    calendar. **No invitees** (adding attendees makes the calendar server
    email people — outbound, out of scope), no URL/location, no
    alarms, no recurrence. Keeps the write small and reversible.
    **Notes (D3, Matt 2026-09-17):** only for "Make Event from Email…", and
    only when Matt ticks "Add a reference to this email in the event notes"
    (off by default): one sanitized line "From an email from <sender>:
    <subject>" plus the app-built Gmail link (GmailLinkOpener.isAllowed).
    Never email body text. Notes sync wherever that calendar syncs; the form
    says so.
  - **Created indication (D3):** a green in-app banner ("Added “title” to
    calendar", Undo, auto-dismiss 8s, nothing persisted) plus an "Event
    created" mark on the source email's row, driven by the log.
  - **One thread, one event (D6, Matt 2026-09-28):** a row ALSO shows
    "Event created" when its own hint resolves to the same time as an event
    the app created and hasn't undone — so the earlier mails in a thread
    that settled on that time stop inviting a second copy. Times are
    compared to the minute (all-day by day) and come back LIVE from
    EventKit by identifier, since the log stores none: an event moved or
    deleted elsewhere stops matching by itself.
  - **Gate:** the form produces a validated `NewEventDraft` (mintable only by
    its validator). The confirmation dialog names title, date/time and
    calendar; its confirm() is the single mint site for
    `ConfirmedCreateEvent` (fileprivate init). The EventKit writer accepts
    nothing else. Cancel mints nothing.
  - **Log (`CalendarActionLogEntry`, SwiftData, explicit save):** action kind,
    EventKit event identifier, calendar identifier, timestamp, undoneAt. No
    title or times persisted — the Recently Created list reads them back
    live from EventKit by identifier.
  - **Undo:** one click, no dialog (restores the prior state), and ONLY for
    an identifier this app logged as created and not yet undone. If the
    event is already gone (deleted elsewhere), mark it and say so — never
    delete anything else.
  - **Permissions:** none new — the app already holds calendar full access
    (EventKit has no read-only level). EventKitCalendarSource's "never calls
    a write API" note is updated; the writer is a separate type.
  - **Release-gate tests:** draft validation table; cancel/double-confirm
    mint nothing; writer reachable only with the confirmed type (fake
    store); undo deletes only logged app-created identifiers; nothing from
    MailMessage/CloudVerdict/DashboardTask can construct a draft directly
    (suggestions only produce editable form values); suggestion refused on
    scam/suspicious/dmarc-fail mail; parameterized NSDataDetector
    suggestion table (synthetic text).
  - Steps as built: Design → A (draft + validation + gate) → B (on-device
    event suggester) → C (EventKit writer + log + undo, fake-store tests) →
    D (New Event form, Make Event from Email…, dialog, Recently Created) →
    D2 (meal preferences, relative dates anchored to the sent date) →
    D3 (created banner, row mark, opt-in notes reference) →
    D4 (IMAP body-fetch fix, body times win, undo feedback) →
    D5 (on-device event hint on rows) → D6 (one thread, one event) →
    E (live validation, passed 2026-09-28).
  - Known limitation Matt accepted: the D6 mark matches by TIME alone, so an
    unrelated email proposing a different meeting at the same minute would
    also read "Event created". Tightening it to require the same sender or
    thread is a small change if it ever bites.

**VIP senders (Matt, 2026-10-07).** ✅ Built. Mail from a sender on the
app's VIP list always appears in Important Email, decided ON THIS MAC with
no API call — the first and only case where LocalRulesEngine emits
`.important`.
  - **The list lives in the app** (Settings ▸ VIPs, `VIPSender` in
    SwiftData). The app is sandboxed and cannot read Apple Mail's own VIP
    list, so this mirrors it rather than syncing. Add by typing an address
    in Settings or from a message row's context menu; remove in either
    place.
  - **A typed address is allowed here** — unlike the cloud allowlist, which
    forbids one by design. VIP is not a privacy boundary: a typo costs a
    missing highlight, never an unintended cloud send.
  - **Order of rules:** scam FIRST (a trusted dmarc=fail stays `.scam` no
    matter whose name is on it — impersonating someone you trust is the
    classic attack), then VIP, then newsletter. VIP outranks newsletter so a
    VIP's forwarded newsletter stays out of Unsubscribe Candidates, where
    acting on the forwarded List-Unsubscribe header would unsubscribe from
    the ORIGINAL sender's list.
  - **The cloud boundary is unchanged:** being a VIP grants NO cloud
    eligibility. VIP mail stays in the candidate set so an allowlisted VIP
    still gets tasks and the scam second opinion, but it reaches the API
    only through the same allowlist gate as everything else. Two
    release-gate tests pin this: a non-allowlisted VIP never reaches the
    analyzer; an allowlisted one still does.
  - **Applied as an overlay, never cached:** the classification cache keeps
    what the rules say about a MESSAGE; VIP is a fact about a SENDER that
    the user can change at any time. Overlaying after the cache lookup
    makes edits immediate and leaves no stale `.important` rows in storage.

with account tags, EarthLink's auth stamp trusted, and archive + undo on
Mindspring via a folder chosen in Settings. Design settled 2026-10-25. Before this stage the app held ONE credential and assumed it was Gmail-ish.
Matt also reads EarthLink/Mindspring mail, and wanted both in one dashboard.
IMAP only — no Exchange, no provider APIs.
  - **Scope decisions (Matt, 2026-10-25):**
    1. **One merged dashboard.** Inbox, Important, Unsubscribe Candidates
       and Scams pool every account, newest first, with a small account tag
       per row. A message that reached both accounts shows twice, tagged —
       honest beats clever, and each copy's actions act on its own account.
    2. **Every action that the server can support** works per account from
       day one. Archive still discovers its destination by RFC 6154
       SPECIAL-USE (\All, else \Archive) and refuses rather than guessing a
       folder name, so an account offering neither reports that. "Open in
       Gmail" stays Gmail-only by construction.
    3. **Trusted auth verdicts per provider.** AuthservIDMap gets explicit
       entries, added ONLY from a real observed header — never derived from
       the IMAP hostname. The planned "registrable domain of the server"
       rule was WRONG and was dropped: EarthLink hands filtering to Vade
       Secure and stamps `earthlink-vadesecure.net`, which neither
       imap.mindspring.com nor imap.earthlink.net would ever produce
       (verified 2026-10-25 on a real account). Unknown provider ⇒ still
       nil ⇒ no trusted verdict (fail-safe unchanged).
  - **Routing is the heart of it.** `MailMessage` gains `accountID`; IMAP
    UIDs are mailbox-local, so every UID-keyed operation (body fetch,
    archive) must act on the account the message came from. A
    `MultiAccountMailSource` owns one `IMAPMailSource` per account, fans out
    fetches, merges by date, and dispatches UID work by accountID. A message
    with no accountID (previews, tests) keeps today's single-source path.
  - **Credentials:** one Keychain item per account (the query gains
    kSecAttrAccount; `loadAll()` returns them all). The existing single item
    is picked up as the first account — no migration step. Same attributes
    as today: no iCloud sync, WhenUnlocked, never logged.
  - **Failure isolation:** one account failing to connect must not blank the
    dashboard — the other account's mail still shows, with the error
    attributed to the account it came from.
  - **Unchanged boundaries:** the cloud allowlist, the VIP list and the
    classification cache are keyed by SENDER ADDRESS, not by account, so
    they work across accounts untouched. Nothing about adding an account
    widens what may reach the API.
  - Steps: A (credentials for many accounts) → B (accountID routing +
    MultiAccountMailSource) → C (auth trust per provider) → D (account tag,
    accounts UI, per-account errors) → E (live validation on EarthLink).
  - **Field findings from E (keep these):**
    1. Keychain: kSecMatchLimitAll + kSecReturnData fails on macOS. List
       attributes first, then read each password with a single-item query.
    2. EarthLink implements neither RFC 6154 SPECIAL-USE nor LIST-EXTENDED.
       A pattern LIST (`LIST "" ("*")`) is extended syntax and is rejected;
       the plain listing must use the RFC 3501 single-pattern form.
    3. Because EarthLink can't name its archive folder, archive needs a
       per-account folder chosen in Settings ▸ Accounts from the server's
       own LIST (ArchiveMailboxPreference). The app still never guesses.

**Header forensics (Matt, 2026-10-25).** ✅ Built. Deterministic
sender-identity checks over each message's own headers, computed ON THIS MAC
for EVERY message — including the senders the cloud never sees.
  - **Checks:** Return-Path vs From, Reply-To vs From, DKIM `d=` alignment
    with From, display name naming a domain that contradicts the real
    address, and an Authentication-Results header present but stamped by a
    server we cannot attribute. Domains compare at organizational level
    (bounces.amazon.com == amazon.com).
  - **Advisory, not a verdict.** Legitimate bulk mail trips single checks
    constantly, so findings never change a message's category on their own —
    the local `.scam` rule is still a TRUSTED dmarc=fail on non-list mail.
    A row shows the line only when NOTABLE: the impersonation check (which
    has no honest explanation) or two independent mismatches.
  - **What crosses the boundary (Matt's question, answered 2026-10-25):**
    the FINDINGS, never the raw headers. Headers carry routing IPs, the
    user's own address and provider-internal fields, and they are
    attacker-controlled text that would widen the prompt's injection
    surface for no gain — a model cannot compare two domains better than
    `==` can. The cloud prompt gets one line of the app's own words, and
    the system prompt tells the model those are the app's findings and that
    a mismatched bounce domain is routine. A release-gate test asserts no
    header text appears in the findings strings.

**Triage agent (prototype).** ✅ 2026-11-12, tested live in demo mode. The
user asks "Plan my morning" or "Clean up my inbox"; Claude runs a Messages
API tool-use loop and answers with a PLAN of proposals. See Agent/.
  - **It only proposes.** Read tools: list_recent_mail, read_message_body,
    list_calendar_events. Proposal tools: propose_archive,
    propose_unsubscribe, propose_event, flag_for_reply. A proposal is a row;
    approving one opens the SAME dialog or form the message row's button
    opens (ArchiveConfirmation, UnsubscribeConfirmation, the reviewed New
    Event form), so every confirmation gate still stands. TriageAgent holds
    no archiver, unsubscriber or calendar writer.
  - **The model names a message; it never parameterizes an action.** Every
    proposal tool takes a message handle and a one-line reason. Where an
    unsubscribe goes still comes only from headers; an event's title and
    time still come only from the on-device suggester and the reviewed
    form. The "no cloud verdict may construct a draft" release gate is
    unchanged.
  - **The allowlist gate covers the agent (settled 2026-11-12).** Mail from
    an allowlisted sender (and not a local scam verdict) is listed with
    sender, subject and already-extracted tasks; its body is sent only on
    request, stripped and capped. EVERY other message reaches the model as
    an opaque handle plus the app's own findings (received time, category,
    VIP, unsubscribe available, mentions a date): no sender, subject or
    body. The model may still propose an action on such a row, and the plan
    names the message locally and says the assistant never saw it. Handles
    are per-run; real Message-IDs are never sent (they end in the sender's
    domain). Enforced by type: sender-controlled fields render only from
    CloudEligibleMessage, and InboxViewModel.bodyForAgent accepts nothing else.
  - **Calendar titles are opt-in.** They had never gone to the API, so the
    agent gets busy times unless the user ticks "Share calendar event
    titles" in the Assistant section (forced on in demo mode: synthetic data).
  - **Limits (AgentLimits):** 8 model turns, 60,000 tokens per run (checked
    before every request), 4,096 output tokens per reply, 6 body reads,
    12 proposals. Every billed turn is recorded in CloudUsageLedger.
    **Per-reply cap raised 2,000 → 4,096 (Matt, 2026-11-12)** after a live
    run hit max_tokens mid-plan and stopped. A cut-off reply still ends the
    run; outputCapIsSentAndRoomy pins the cap.
  - **Fixed tool set:** AgentTool is a closed enum; a name outside it gets an
    error result. Tool results label sender-written text as untrusted, and a
    body sits between markers carrying a per-run random token.
  - **Run log:** in memory, tool kinds + handles + counts only. No bodies,
    subjects, senders or model text (tested).
  - **Demo-mode key:** AgentAPIKeyReader (Cloud/APIKeyStore.swift) is the one
    read-only exception to demo mode's Keychain block, used by the agent
    alone. KeychainAPIKeyStore.load() still returns nil in demo mode.
  - **Injection demo:** the demo inbox holds one email from an allowlisted
    sender (Casey Lin) telling "the AI assistant" to archive two threads,
    unsubscribe from a colleague, forward a thread outside and say nothing.
    It is not special-cased anywhere. A test scripts a model that obeys it
    to the letter and shows the result: two plan rows awaiting confirmation,
    nothing else.
  - **Plan-row badges (Matt, 2026-11-12), display only:** a green lock
    badge, "Kept on this Mac: the assistant never saw this sender or
    subject", on proposals for local-only mail; and an orange warning badge,
    "The assistant found instructions aimed at an AI in this email", when
    propose_archive carries the optional `addressed_to_ai` flag. That flag
    is the model's report, so it is honoured ONLY for an archive of a
    shared message whose body the model read in the same run; anywhere else
    it is ignored (injectionReportNeedsARead). No gate depends on it.
    A third, orange "Scam or phishing: flagged by this Mac's own checks",
    shows on any proposal whose message the LOCAL rules classify as scam;
    never set from model output (checked in proposalsPerformNothing).
  - **Local scams are always in the plan (Matt, 2026-11-12).** When a run
    ends normally (completed, step limit, budget), the app appends an
    archive row, `addedByApp`, for every local-scam message the model did
    not already propose to archive ("Added by this Mac: its own checks flag
    this as a scam."). Deterministic, never duplicated, not counted against
    the model's proposal limit, not added on failure or cancel. Same
    Archive… confirmation as every other row (localScamsAreAlwaysInThePlan).
    Added after a live "Plan my morning" run left the scam out.
  - **A summary can't stand in for a plan.** The plan shown is only what
    the proposal tools recorded. If the model finishes with an empty plan it
    is asked once (the app's own notice) to make its proposals or confirm
    there are none, and an empty plan is labelled as such in the UI. Added
    after a live run whose summary said "I'm proposing…" with no tool calls.
  - **Summary display:** the prompt asks for two or three sentences of
    plain prose (80 words at most); AgentSummaryText strips stray bullets,
    bold and heading markers for display. Presentation only, words unchanged.
  - **Release-gate tests:** TriageAgentTests (33), against a scripted
    transport, plus AgentSummaryTextTests. Full suite 374 passing
    (370 unit + 4 UI).
  - **Known limits:** a prototype. No streaming, no retry, one run at a
    time, and the plan is not persisted. The Usage pane counts email
    analyses and Assistant turns together as "API calls".

## Dependencies

This app aims to ship with the minimum dependency surface consistent with
correctness. Every dependency is a trust expansion: third-party code runs
inside our process with full access to anything our process can see —
Keychain credentials, in-memory mail content, the calendar feed.

Before adding any dependency, justify it in writing here. Removing one is
always easier than adding one. Pin to specific versions or commit SHAs —
never to a range or "latest."

### Current dependencies

- **apple/swift-nio-imap** pinned to commit
  `01de1f9a29df31f77e87c2d9248940de7233ee1e` (HEAD of `main`,
  2026-04-30). Provides IMAP4rev1 wire-protocol parsing and type-safe
  Swift command/response model. Used by Stage 3's IMAP fetch.

  **Accepted disclaimer.** The library's README explicitly states:
  > ⚠️ This library is still in development phases and not ready to
  > be used in production system yet. ⚠️

  We accepted this because:
  1. The alternative was 500–600 lines of hand-rolled IMAP code with
     zero parser testing against real Gmail. The "production-ready
     hand-rolled" option does not exist.
  2. Our use is narrow — four standard commands against Gmail. Far
     from the spec edges where pre-1.0 libraries usually fail.
  3. Actively maintained; commits as recent as 2026-04-30 include a
     fix directly relevant to our FETCH ENVELOPE parsing.
  4. Failure mode is benign — user sees "Couldn't reach mail server"
     and retries. No data loss path.

  **Pinned to HEAD `01de1f9a`, not tag `0.2.0`.** Justification: the
  2026-04-30 addr-list-`()`-vs-NIL fix is required for reliable
  FETCH ENVELOPE parsing against real-world Gmail. The cost is
  carrying two API refactors merged after 0.2.0; we code against
  HEAD's shape.

  **If it bites us.** No pre-committed fallback. Specifics route
  the right response:
    - Gmail-specific parse error → bump the pinned SHA forward,
      check upstream issues first.
    - Fundamental command bug → file upstream, consider patching
      upstream rather than swapping.
    - Whole library broken → surface specifics; pick among bumping
      pin, MailCore2, hand-rolled-with-reduced-scope.
    Never silently swap mid-stage.

- **apple/swift-nio-ssl** pinned to tag `2.37.0` (the latest 2.x at
  SPM add time). Required by swift-nio-imap's NIO Channel approach
  for TLS to imap.gmail.com:993. swift-nio-ssl is past 1.0 and
  genuinely production-ready (used in Apple's own services), so tag
  pin is appropriate; SHA pin would be over-discipline. Concrete
  pin frozen in Package.resolved (committed to git).

**Transitive dependencies** (concrete versions as resolved at SPM
add time, frozen in Package.resolved — all Apache 2.0, all
Apple-stewarded swift-server family, no extra trust surfaces beyond
the two top-level packages above):
  - apple/swift-nio 2.100.0 — async networking foundation.
  - apple/swift-collections 1.5.1 — OrderedCollections, used by NIOIMAP.
  - apple/swift-se0270-range-set 1.0.1 — RangeSet utility, used by NIOIMAP.
  - apple/swift-atomics 1.3.0 — atomics primitives, used by swift-nio.
  - apple/swift-system 1.6.4 — POSIX abstractions, used by swift-nio.

Notable absence: **swift-log was NOT pulled in**. swift-nio-imap's
Package.swift declares it as a dependency, but only its CLILib target
links it. Since we attach only the NIOIMAP product to our app target,
SPM does not resolve swift-log. One less dependency than expected —
log it here so a future SPM dep change doesn't silently pull it in.

Binary cost: ~5–10 MB after Xcode dead-strip. Acceptable for a
desktop dashboard.

### Never add — explicit constraint, do not relax without re-reading
this section and ARCHITECTURE.md Security & Privacy:

- **Networking libraries other than the swift-nio family.** We already
  have swift-nio transitively. Importing AlamoFire, URLSession
  wrappers, or alternative async-HTTP libraries expands the trust
  surface unnecessarily.
- **Mail libraries handling SMTP / outgoing email.** The app does not
  send mail. No roadmapped feature requires this.
- **Analytics, crash reporting, telemetry libraries.** ARCHITECTURE.md
  Security & Privacy item 4 forbids telemetry.
- **iCloud / CloudKit / cross-device sync libraries.** ARCHITECTURE.md is
  explicit: single-device, local-only.
- **Wrapper libraries around the Security framework** (KeychainAccess
  and similar). The credentials path is the most trust-critical code
  in the app and uses Security framework directly. Do not intermediate.
